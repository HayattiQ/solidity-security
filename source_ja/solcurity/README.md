# Solcurityスタンダード

**Solidityスマートコントラクト**のための独自の見解に基づいた**セキュリティ**と**コード品質**の基準。

_[BoringCrypto](https://github.com/sushiswap/bentobox/blob/master/documentation/checks.txt)、[Mudit Gupta](https://www.youtube.com/watch?v=LLiJK_VeAvQ)、[Runtime Verification](https://github.com/runtimeverification/verified-smart-contracts/wiki/List-of-Security-Vulnerabilities)、および[ConsenSys Diligence](https://consensys.github.io/smart-contract-best-practices/attacks/)の作業に基づいています_。

### 一般的なレビューアプローチ：
- プロジェクトのドキュメント、仕様書、ホワイトペーパーを読んで、スマートコントラクトが何をするためのものかを理解します。
- コードを確認する前に、コントラクトがどのようなものになるかの心理的モデルを構築します。
- プロジェクトのアーキテクチャを把握するために、コントラクトを一瞥します。Suryaのようなツールが役立ちます。
- アーキテクチャを心理的モデルと比較します。驚くべき領域を調査します。
- 脅威モデルを作成し、理論的な高レベルの攻撃ベクトルのリストを作成します。
- 価値交換ができる領域を見てください。特に`transfer`、`transferFrom`、`send`、`call`、`delegatecall`、`selfdestruct`のような関数。それらから逆方向に進み、適切に保護されていることを確認します。
- 外部コントラクトとインターフェースする領域を見て、シェア価格が上昇するだけなど、それらに関するすべての前提が有効であることを確認します。
- コントラクトの一般的な行ごとのレビューを行います。
- 脅威モデル内のすべてのアクターの視点から別のレビューを行います。
- プロジェクトのテスト+コードカバレッジを一瞥し、カバレッジが不足している領域をより深く見ます。
- Slither/Solhintのようなツールを実行し、その出力をレビューします。
- 関連するプロジェクトとその監査を見て、類似の問題や見落としがないか確認します。

- `F6` - チェックを効果の前に行うパターンは守られていますか？（SWC-107）
- `F7` - approve関数のようなフロントランニングの可能性をチェックします。（SWC-114）
- `F8` - 不十分なガスによるグリーフィングは可能ですか？（SWC-126）

- `F10` - 戻り値は常に割り当てられていますか？
- `F11` - 関数が正しく実行されるために、状態に関する不変条件を書き出してテストします。
- `F12` - 関数が実行された後の戻り値や状態の変化に関する不変条件を書き出してテストします。
- `F13` - 関数の命名には注意してください。人々は名前に基づいて動作を想定するからです。
- `F14` - 関数が意図的に安全でない場合（ガスを節約するためなど）、そのリスクに注意を引くために扱いにくい名前を使用してください。
- `F15` - すべての引数、戻り値、副作用、その他の情報はnatspecを使用して文書化されていますか？
- `F16` - 関数がシステム内の別のユーザーに対する操作を許可する場合、`msg.sender`が操作されるユーザーであると仮定しないでください。
- `F17` - 関数がコントラクトが初期化されていない状態であることを要求する場合、明示的な`initialized`変数をチェックします。代わりに`owner == address(0)`や他の類似したチェックを使用しないでください。
- `F18` - 子コントラクトが関数を呼び出すのを意図的に防ぐ場合にのみ`private`を使用し、柔軟性のために`internal`を優先してください。
- `F19` - 子コントラクトが関数の動作を上書きしたい正当な（そして安全な）インスタンスがある場合は、`virtual`を使用してください。

## コード

- `C1` - SafeMathまたは0.8のチェック付き数学を使用していますか？（SWC-101）
- `C2` - 複数回読み取られるストレージスロットはありますか？
- `C3` - DoSを引き起こす可能性のある無制限のループ/配列が使用されていますか？（SWC-128）
- `C4` - `block.timestamp`は長い間隔にのみ使用してください。（SWC-116）
- `C5` - 経過時間にblock.numberを使用しないでください。（SWC-116）
- `C7` - 特に外部（信頼されていても）コントラクトへのdelegatecallは可能な限り避けてください。（SWC-112）
- `C8` - 配列を反復処理中にその長さを更新しないでください。
- `C9` - ランダム性に`blockhash()`などを使用しないでください。（SWC-120）
- `C10` - 署名はノンスと`block.chainid`でリプレイから保護されていますか（SWC-121）
- `C11` - すべての署名がEIP-712を使用していることを確認してください。（SWC-117 SWC-122）
- `C12` - 2つ以上の動的型を使用する場合、`abi.encodePacked()`の出力をハッシュ化しないでください。一般的には`abi.encode()`の使用を優先してください。（SWC-133）
- `C13` - アセンブリには注意し、任意のデータを使用しないでください。（SWC-127）
- `C14` - 特定のETH残高を想定しないでください。（SWC-132）
- `C15` - 不十分なガスによるグリーフィングを避けてください。（SWC-126）
- `C16` - プライベートデータはプライベートではありません。（SWC-136）
- `C17` - メモリ内の構造体/配列を更新しても、ストレージ内のそれは変更されません。
- `C18` - 状態変数をシャドウイングしないでください。（SWC-119）
- `C19` - 関数パラメータを変更しないでください。
- `C20` - 値をその場で計算する方が保存するよりも安いですか？
- `C21` - すべての状態変数は正しいコントラクト（マスターvsクローン）から読み取られていますか？
- `C22` - 比較演算子（`>`、`<`、`>=`、`<=`）は正しく使用されていますか？特に1つずれのエラーを防ぐために。
- `C23` - 論理演算子（`==`、`!=`、`&&`、`||`、`!`）は正しく使用されていますか？特に1つずれのエラーを防ぐために。
- `C24` - 乗算がオーバーフローする可能性がある場合を除き、常に除算の前に乗算してください。
- `C25` - マジックナンバーは直感的な名前を持つ定数に置き換えられていますか？
- `C26` - ETHの受信者がリバートするフォールバック関数を持っていた場合、DoSを引き起こす可能性がありますか？（SWC-113）
- `C27` - SafeERC20を使用するか、戻り値を安全にチェックしてください。
- `C28` - ループ内で`msg.value`を使用しないでください。
- `C29` - 再帰的なdelegatecallが可能な場合（コントラクトが`Multicall`/`Batchable`を継承している場合など）、`msg.value`を使用しないでください。
- `C30` - `msg.sender`が常に関連するユーザーであると仮定しないでください。
- `C31` - ファジングや形式検証以外では`assert()`を使用しないでください。（SWC-110）
- `C32` - 認証に`tx.origin`を使用しないでください。（SWC-115）
- `C33` - `address.transfer()`や`address.send()`を使用しないでください。代わりに`.call.value(...)("")`を使用してください。（SWC-134）
- `C34` - 低レベル呼び出しを行う場合、呼び出す前にコントラクトが存在することを確認してください。
- `C35` - 多くのパラメータを持つ関数を呼び出す場合、名前付き引数構文を使用してください。
- `C36` - create2にアセンブリを使用しないでください。現代のソルトされたコントラクト作成構文を優先してください。
- `C37` - chainidやコントラクトのコード/サイズ/ハッシュにアクセスするためにアセンブリを使用しないでください。現代のSolidity構文を優先してください。
- `C38` - 変数をゼロ値（`0`、`false`、`""`など）に設定する場合は、`delete`キーワードを使用してください。
- `C39` - できるだけ「なぜ」をコメントしてください。
- `C40` - 難解な構文を使用したり、非従来的なコードを書いたりする場合は、「何を」コメントしてください。
- `C41` - 複雑な計算や固定小数点数学の隣に、説明と入力/出力例をコメントしてください。
- `C42` - 最適化が行われる場所には、それらが節約するガスの見積もりとともに説明をコメントしてください。
- `C43` - 特定の最適化が意図的に避けられる場所には、実装された場合にどれだけのガスを節約する/しないかの見積もりとともに説明をコメントしてください。
- `C44` - オーバーフロー/アンダーフローが不可能な場所、または人間のタイムスケールでオーバーフロー/アンダーフローが非現実的な場所（カウンターなど）では、`unchecked`ブロックを使用してください。`unchecked`が使用される場所には、それが節約するガスの見積もり（関連する場合）とともに説明をコメントしてください。
- `C45` - Solidityの算術演算子の優先順位ルールに依存しないでください。デフォルトの演算子優先順位を上書きするための括弧の使用に加えて、それを強調するためにも括弧を使用する必要があります。
- `C46` - 論理/比較演算子（`&&`/`||`/`>=`/`==`/など）に渡される式は副作用を持つべきではありません。
- `C47` - 精度の損失をもたらす可能性のある算術演算が行われる場所では、それがシステム内の適切なアクターに利益をもたらすことを確認し、コメントで文書化してください。
- `C48` - リエントランシーロックが使用される場合は常に、インラインまたは`@dev` natspecコメントでその必要性の理由を文書化してください。
- `C49` - 特定の数値範囲でのみ動作する関数をファジングする場合、ファザーの入力を絞り込むためにモジュロを使用してください（例えば、`x = x % 10000 + 1`で1から10,000に制限する）。
- `C50` - 可能な限り、分岐ロジックを簡素化するために三項式を使用してください。
- `C51` - 複数のアドレスを操作する場合、それらが同じである場合に何が起こるかを自問してください。

## コントラクト

- `T1` - SPDXライセンス識別子を使用してください。
- `T2` - ストレージを変更するすべての関数に対してイベントが発行されていますか？
- `T3` - 正しい継承をチェックし、シンプルで線形に保ちます。（SWC-125）
- `T4` - コントラクトが転送されたETHを受け入れるべき場合は、`receive() external payable`関数を使用してください。
- `T5` - 保存された状態間の関係に関する不変条件を書き出してテストします。
- `T6` - コントラクトの目的と他のコントラクトとどのように相互作用するかはnatspecを使用して文書化されていますか？
- `T7` - 別のコントラクトが完全な機能を解除するために継承する必要がある場合、コントラクトは`abstract`としてマークされるべきです。
- `T8` - 他の場所で変更された場合にイベントを発行する非イミュータブル変数がコンストラクタで設定される場合、適切なイベントを発行してください。
- `T9` - 過度の継承は複雑さを隠し、過度の抽象化を促進するため、避けてください。
- `T10` - 常に名前付きインポート構文を使用して、別のファイルからどのコントラクトがインポートされているかを明示的に宣言してください。
- `T11` - インポートをフォルダ/パッケージでグループ化します。グループは空行で区切ります。外部依存関係のグループが最初に来て、次にモック/テストコントラクト（関連する場合）、最後にローカルインポートが来るべきです。
- `T12` - `@notice` natspecコメントでコントラクトの目的と機能を要約してください。コントラクトがプロジェクト内外の他のコントラクトとどのように相互作用するかを`@dev` natspecコメントで文書化してください。

## DeFi

- `D1` - 他のコントラクトが何をするか、何を返すかについての前提をチェックしてください。
- `D2` - 内部会計と実際の残高を混同しないでください。
- `D3` - AMMからのスポット価格をオラクルとして使用しないでください。
- `D4` - オフチェーンまたはオラクルを介して価格目標を受け取らずにAMMで取引しないでください。
- `D5` - オラクル/価格操作を防ぐために健全性チェックを使用してください。
- `D6` - リベーシングトークンに注意してください。それらがサポートされていない場合は、その特性が文書化されていることを確認してください。
- `D7` - ERC-777トークンに注意してください。信頼しているトークンでも、ERC-777であればリエントランシーを実行する可能性があります。
- `D8` - 転送時手数料トークンに注意してください。それらがサポートされていない場合は、その特性が文書化されていることを確認してください。
- `D9` - 小数点が多すぎるまたは少なすぎるトークンに注意してください。サポートされる最大値と最小値が文書化されていることを確認してください。
- `D10` - 収益を決定するためにコントラクトの生のトークン残高に依存することに注意してください。直接送信された資産を回収する方法を提供するコントラクトは、アドレスの生のイーサまたはトークン残高に依存するシェア価格関数を台無しにする可能性があります。
- `D11` - あなたのコントラクトがトークン承認のターゲットである場合、ユーザー入力から任意の呼び出しを行わないでください。
