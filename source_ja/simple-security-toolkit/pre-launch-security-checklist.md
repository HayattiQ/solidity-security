# ローンチ前セキュリティチェックリスト

- [ ]  GitHubの`README.md`ファイルに、セキュリティ連絡先メールアドレスを目立つように表示する。チームの誰かが実際にそれらのメールを受信することを確認する。
- [ ]  GitHubリポジトリに、コントラクトがデプロイされているアドレスが記載されていることを確認する。
- [ ]  UIからGitHubリポジトリへのリンクがあることを確認する。
- [ ]  デプロイされたコードにセキュリティ監査で提案されたパッチが含まれていることを確認する。監査が実施された後でも、これらのパッチが適用される前にコードがデプロイされる可能性があります。
- [ ]  ドラフト監査レポートで推奨されたすべての変更に対応し、監査人があなたの回答を含む最終版のレポートを公開するようにする。
- [ ]  監査中にコードに多数の推奨変更を受け取った場合は、変更を加えた後に2回目の監査を受けることを強く検討する必要があります。理想的には別の監査人から。長いリストの問題がある監査は、監査人がより多くの時間を与えられればさらに多くの問題を発見したであろうことを示していることがよくあります。
- [ ]  Etherscanでコントラクトを[検証](https://etherscan.io/verifyContract)する。[Foundry](https://book.getfoundry.sh/forge/deploying.html?highlight=verify#verifying)や[Hardhat](https://hardhat.org/plugins/nomiclabs-hardhat-etherscan.html)には、検証を支援する自動化ツールがあります。
- [ ]  バグ報奨金プログラムを設定する。[Immunefi](https://immunefi.com/)や[HackerOne](https://www.hackerone.com/)がコーディネートを手伝ってくれます。高重大度の問題に対して適切と最初に考える報奨金は、おそらく2〜10倍に増やすべきです（ローンチ後、最低限は危険にさらされている価値の1％であるべきです）。
- [ ]  モニタリングとアラートを設定する。セキュリティインシデントに迅速に対応できるように、プロジェクトで何が起きているかを把握したいでしょう。例えば、新しいガバナンス提案を監視し、それらが発生したときにアラートを出すスクリプトを持つことができます。または、TWAPを使用している場合、ブロックごとにTWAPをチェックし、CEXからの価格フィードと比較して、10％以上異なる場合にアラートを出すスクリプトを持つことができます。または、コントラクト内のトークンの20％以上が単一のトランザクションで削除された場合にアラートを出すことができます。[Check the Chain](https://github.com/checkthechain/checkthechain) + [Grafana](https://grafana.com/)のようなツールを使用するか、[Tenderly](https://tenderly.co/alerting)やOpenZeppelinの[Defender Sentinels](https://www.openzeppelin.com/defender)のような既製のモニタリングツールを使用することができます。
- [ ]  エクスプロイトが発生した場合にコントラクトを一時停止したり、他の防御アクションを取るための緊急アクションスクリプトを準備する。
- [ ]  インシデント対応計画を作成する。ハッキングが発生した場合、誰が緊急対応室にいるか、どのプラットフォーム（Discord、Signalなど）とどのチャンネルを使用して通信するか、防御アクションをどのように実行するかを事前に知っておきたいでしょう。これらすべてをどこかのドキュメントに記載しておくと、アドレナリンが判断を曇らせているときに頼りになります。[このテンプレート](https://github.com/nascentxyz/simple-security-toolkit/blob/main/incident-response-plan-template.md)を使用して準備することができます。
