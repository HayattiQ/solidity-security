# 監査準備チェックリスト

### 最低限の品質チェックリスト

- [ ]  Solidityの[最新](https://docs.soliditylang.org/en/latest/)メジャーバージョンを使用する。
- [ ]  可能な限り既知/確立されたライブラリを使用する。[OpenZeppelinコントラクト](https://github.com/OpenZeppelin/openzeppelin-contracts/)は、セキュリティを何よりも優先しており、ほとんどの監査人がすでに精通しているため、推奨されます。ガス最適化が最も重要な機能には、[Solmateコントラクト](https://github.com/Rari-Capital/solmate)が良い代替手段となります。
- [ ]  「ハッピーパス」のユーザーストーリーのテストと、失敗するはずのアクションに対してリバートを期待するテストを持つ。すべてのテストが合格している必要があります。
- [ ]  ファズテストを組み込む。ファジングはバグを発見するのに非常に効果的であることが証明されています。[Foundry](https://github.com/foundry-rs/foundry)や[Echidna](https://github.com/crytic/echidna)のようなツールは、ステートレスとステートフルの両方のファジングを可能にします。[Foundry Invariantsリファレンスガイド](https://book.getfoundry.sh/forge/invariant-testing?highlight=invariant#invariant-testing)は、ファジング用のコントラクト不変条件の設定方法の概要を提供しています。[Hardhat](https://github.com/NomicFoundation/hardhat)を使用している場合は、テスト機能を強化するために上記のツールの1つを含めることも価値があります。
- [ ]  静的解析ツール（[Slither](https://github.com/crytic/slither)が推奨、[MythX](https://mythx.io/)は代替手段）をコードで実行し、その結果を検討する。これらは非常に頻繁に問題でないものにフラグを立てますが、時には簡単な問題を捕捉することができるので、実行する価値があります。
- [ ]  デプロイスクリプトとモックアップグレードスクリプト（該当する場合）を準備し、監査範囲の一部として含める。デプロイメントとアップグレードはランタイムコードと同様に重要であり、同じレベルのセキュリティ注意が必要です。
- [ ]  すべての関数を文書化する。`public`/`external`関数には[NatSpecドキュメント](https://docs.soliditylang.org/en/develop/natspec-format.html)を使用する。これはコントラクトの公開インターフェースの一部と考えてください。
- [ ]  コンパイラからのエラーや警告なしにコントラクトがコンパイルされる。
- [ ]  コードをスペルチェッカーにかける。
- [ ]  可能な限りアセンブリの使用を避ける。アセンブリを使用すると、Solidityのガードレールを捨て、より慎重にチェックする必要があるため、監査時間が増加します。
- [ ]  `unchecked`の使用を文書化する。各コードブロックで算術チェックを実行しない*理由*を具体的に説明する。できれば各操作ごとに。
- [ ]  `external`にできる`public`関数はすべて`external`にする必要があります。これはガスの考慮だけでなく、関数が呼び出される可能性のあるコンテキストの数を減らすことで、監査人の認知的負担も軽減します。
- [ ]  可能な限り[Function Requirements-Effects-Interactions-Protocol Invariants (FREI-PI)パターン](https://www.nascent.xyz/idea/youre-writing-require-statements-wrong)を使用する。すべてのトークンとETH転送を「インタラクション」として扱う。各インタラクションの終わりにシステムレベルのプロトコル不変条件がまだ保持されていることを確認する。
- [ ]  少なくとも1人の信頼できるSolidity開発者またはセキュリティ担当者に、組織外からコントラクトの健全性チェックをしてもらう。あなたのコードが大きな変更を必要とする状態であれば、高価な監査の後ではなく、早い段階で信頼できる友人から（無料で）それを聞きたいでしょう。


### あると良いもの

- [ ]  不変条件を検証するために形式検証ツールを使用するが、実際には現在の形式検証ツールは万能ではなく、処理されない一部のエッジケースがあることに注意する。[Certora](https://www.certora.com/)と[Runtime Verification](https://runtimeverification.com/)は、このカテゴリでよく使用される（有料の）ツールの例です。
- [ ]  外部のセキュリティ前提条件を書き留める。これは超形式的である必要はありません。例えば、「`owner`が悪意を持っていないこと、Chainlinkオラクルがトークン価格について嘘をつかないこと、Chainlinkオラクルが少なくとも24時間ごとに価格を報告すること、`owner`が承認するすべてのトークンが転送フックのないERC20準拠トークンであること、30ブロック以上のチェーンの再編成が発生しないこと、を前提としています。」これにより、*たとえコントラクトにバグがなくても*、どのように問題が発生する可能性があるかを理解するのに役立ちます。優れた監査人は、あなたの前提条件が現実的かどうかを理解するのを助けることができます。また、あなたが気づいていなかった前提条件を指摘することもできるかもしれません。
- [ ]  自分のコードについて不明な点がある場合、または監査人により多くの時間を費やしてほしい領域がある場合は、これらのリストを作成して監査人と共有する。
