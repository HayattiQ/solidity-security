# 開発プロセス
安全なコードベースを持つための最も重要な要素の一つは、堅実な開発プロセスです：「予防は治療に勝る」。このドキュメントでは、[Nascent](https://www.nascent.xyz)で私たちが上手く機能していると感じている開発プロセスの*例*を示しています。全体的なコード品質を向上させることに加えて、このプロセスは[監査準備チェックリスト](audit-readiness-checklist.md)の補完として機能します。以下のプロセスに従えば、チェックリストの項目のほとんどを自然にクリアすることができるでしょう。

```
機能要求
 |
 └> 仕様
     |
     └> 評価（時間 + 複雑さ + リスク）
        |
        └> 実装
           |
           └> テスト
              |
              └> デプロイメント
                 |
                 └> モニタリング
```
## 仕様
機能に影響を与える変数の種類を記録します：
1. ユーザー入力？
2. 時間？
3. 他のプロトコル？
4. 既存の状態？

## 評価
以下を評価するための専用の時間を設けます：
1. これは現実的にどれくらいの時間がかかるか？仕様がなければほとんどの見積もりは間違っています
2. 仕様が過度に複雑ではないか？複雑さはバグや全体的なコードの質の低下につながります
3. この機能に関連するリスクは何か？これを評価するために十分な時間を費やしてください。機能が触れる可能性のあるすべてのモジュールを検討してください。次に、除外されたモジュールを再確認し、それらが影響を受ける*可能性がない*ことを確認してください

すでに何百万ドルものリスクがあるか、またはローンチ後にそうなる可能性があります。そのため、各機能がそれら*すべて*をどのようにリスクにさらす可能性があるかを検討する**必要があります**。失敗のコストは、おそらく数百万ドルになるでしょう。
## 実装
1. PRのドラフトを作成する
  - 機能要求 + 仕様を含める
2. 初期実装を書く
  - 初期実装を配置する
  - ユーザーのエントリーポイントとなる関数には[Function Requirements-Effects-Interactions-Protocol Invariants (FREI-PI)パターン](https://www.nascent.xyz/idea/youre-writing-require-statements-wrong)に従う
  - すべての関数の意図された動作を文書化し（public/external関数には[NatSpec](https://docs.soliditylang.org/en/develop/natspec-format.html)を使用）、インラインドキュメント/コメントを追加する
  - `unchecked`の使用には以下のような`safety`ドキュメントを含める：
    ```solidity
    // Safety:
    //  1. a + b: aとbはuint64で、aはuint128にキャストアップされるため、uint128(uint64) + uint64
    //     はオーバーフローしない
    //  2. c * 2: cはuint256にキャストアップされるため、uint256(uint128) * 2はオーバーフローしない
    uint256 d;
    unchecked {
      uint128 c = uint128(a) + b;
      d = uint256(c) * 2;
    }
    ```
  - アセンブリの**すべて**の行にドキュメント/コメントを付ける

## テスト

3. 初期の具体的な[テスト](https://book.getfoundry.sh/forge/tests.html)を書く
  - 実装の初期テストを書きます。ストレージへの各書き込みをチェックし、各リバートをチェックする必要があります。実装の各行について、ストレージへの書き込みを探します
  - 状態を変更しない関数の場合、数学的計算を行うコントラクトを継承するテストコントラクトを持つことが良い習慣です
  - カバレッジツール（Foundryの[カバレッジツール](https://github.com/foundry-rs/foundry/pull/1576)など）を使用して、テストがコードをどの程度カバーしているかを確認します
4. 実装をクリーンアップする
5. テストを改善し、発見されたバグに基づいてステップ4に戻る
6. [slither](https://github.com/crytic/slither)を実行する
  - 出力を分析し、必要に応じてステップ4に戻る
7. [ファズテスト](https://book.getfoundry.sh/forge/fuzz-testing.html)を書く
  - 実装に自信を持ったら、それに猿を投げつけます。良いファズテストは、すべての有効な入力を考慮し、可能な限り多くの状態遷移アサーションを含むべきです（この関数は単調に増加/減少するか、常に他の何かより小さいべきか、など）
8. バグが見つかった場合はステップ4に戻る
9. 統合テストを書く
  - あなたの機能は今、おそらくあなたが考えている通りに動作します。複雑なシステムでは、それだけでは不十分です。理想的には、それがシステム全体にどのように影響するかもテストしています。[Foundry](https://github.com/foundry-rs/foundry)と[Echidna](https://github.com/crytic/echidna)を使用した状態テストにより、システム全体の不変条件をテストすることができます。
10. バグが見つかった場合はステップ4に戻る
11. ドキュメントをクリーンアップする
12. CIをセットアップする
  - Github Actionsを通じた継続的インテグレーションは、レビュアーの基本的な作業を支援します
  - [Foundry CI](https://github.com/foundry-rs/foundry-toolchain)と[Slither CI](https://github.com/foundry-rs/forge-template/blob/36f0bf7cbc953f071027a1c1783e7e5c7d9613ed/.github/workflows/lint.yml)が役立ちます。[forge-template](https://github.com/foundry-rs/forge-template)を使用すれば、両方が最初から利用できます
13. PRレビュー
  - 実装者は最初の防衛線に過ぎません。レビュアーの場合は、実装者が上記の原則（状態遷移ごとのテスト、リバートごとのテスト、ファズテスト、統合テスト）に従っていることを確認してください
  - ドキュメントをレビューし、実装が文書化された動作と一致することを確認してください。一致しない場合は、実装者と連絡を取り、どちらを更新する必要があるかを確認してください
  - CIが合格することを確認する
  - 一般的なミスを確認する（[リエントランシー、チェック-エフェクト-インタラクションパターンなど](https://docs.soliditylang.org/en/latest/security-considerations.html#pitfalls)）


## デプロイメント
14. デプロイメントスクリプトを書く
  - Foundryには、ローカルフォーク上でデプロイメントをテストするための[スクリプティングガイド](https://book.getfoundry.sh/tutorials/solidity-scripting)があります。
15. デプロイメントテストを書く
  - デプロイメントが計画通りに進むことを確認するために、*すべての状態遷移*をテストするテストを書き、予期しない変更が発生しないようにします。これを達成する一つの方法は`record`チートコードです。既存のプロトコルをアップグレードする場合は、プロトコル全体のアドレスのリストを作成し、recordを呼び出し、アップグレードを実行します。次に、プロトコルの各アドレスに対して`accesses`を呼び出します。予期せず変更されたスロット/アドレスがないことを確認します
16. 監査を実施する
  - この機能/コントラクトに監査が必要かどうかを検討してください。常に安全側に倒して考えてください
  - 複雑さとコードサイズによって、コントラクトを監査すべきかどうか、誰が監査すべきかを判断します
  - Nascentでは、監査人の品質に関する内部ティアリストがあります。他の開発者に、どの監査人が良くて、どの監査人がそうでないかを確認する必要があります。一部の監査人は、プロトコルのためにボックスにチェックを入れるだけですが、他の監査人は実際に脆弱性を見つけることに関心を持っています
17. 監査の修正を実装する
18. モニタリングサービスをセットアップする
  - システムの重要な側面を監視する内部ツールを持つ
  - [Check the Chain](https://github.com/checkthechain/checkthechain) + [Grafana](https://grafana.com/)のようなツールを使用するか、[Tenderly](https://tenderly.co/alerting)やOpenZeppelinの[Defender Sentinels](https://www.openzeppelin.com/defender)のような既製のモニタリングツールを使用します。
19. [インシデント対応計画](incident-response-plan-template.md)を準備/更新する
20. コントラクトをデプロイする
  - おめでとうございます、あなたはおそらく安全な開発 + デプロイメントの面でSolidity開発者の99%を上回りました

## モニタリング
21. 次の数時間を監視する
  - セットアップしたモニタリングサービスを使用して、予期しない動作を注意深く監視し、行動を起こす準備をしてください
22. リラックスして、ビールを飲みましょう。あなたはそれを獲得しました。
