## コード品質と開発プラクティス

### 一般的なコード品質

- [ ] Solidityの最新メジャーバージョンを使用している
- [ ] コンパイラからのエラーや警告なしにコントラクトがコンパイルされる
- [ ] SPDXライセンス識別子が使用されている
- [ ] コードがスペルチェッカーにかけられている
- [ ] 可能な限りアセンブリの使用を避けている
- [ ] 複雑なロジックには適切なコメントが付けられている
- [ ] マジックナンバーは直感的な名前を持つ定数に置き換えられている
- [ ] 複雑な計算や固定小数点数学には説明と入力/出力例がコメントされている

### 変数と型

- [ ] 変数の可視性が明示的に設定されている（SWC-108）
- [ ] 変数が`internal`にできる場合は`internal`にしている
- [ ] 変数が`constant`にできる場合は`constant`にしている
- [ ] 変数が`immutable`にできる場合は`immutable`にしている
- [ ] 変数の目的とその他の重要な情報がnatspecを使用して文書化されている
- [ ] 隣接するストレージ変数がパックされている
- [ ] 完全な256ビットタイプが適切に使用されている
- [ ] パブリック配列の場合、完全な配列を返す別の関数が提供されている

### 関数

- [ ] 関数の可視性が適切に設定されている
- [ ] 関数が`external`にできる場合は`external`にしている
- [ ] 関数が`internal`にすべき場合は`internal`にしている
- [ ] 関数が`payable`にすべき場合は`payable`にしている
- [ ] 関数の命名が適切で、その動作を正確に反映している
- [ ] すべての引数、戻り値、副作用、その他の情報がnatspecを使用して文書化されている
- [ ] 戻り値が常に割り当てられている
- [ ] 関数パラメータが変更されていない

### モディファイア

- [ ] （リエントランシーロックを除いて）モディファイア内でストレージの更新が行われていない
- [ ] モディファイア内で外部呼び出しが避けられている
- [ ] モディファイアの目的とその他の重要な情報がnatspecを使用して文書化されている

### 構造体とイベント

- [ ] 構造体のフィールドが（可能であれば）一緒にパックされている
- [ ] 構造体の目的とすべてのフィールドがnatspecを使用して文書化されている
- [ ] イベントの関連フィールドがインデックス化されている
- [ ] イベントがいつ発行されるか、およびすべてのフィールドがnatspecを使用して文書化されている

## セキュリティ脆弱性

### リエントランシー

- [ ] チェックを効果の前に行うパターン（checks-effects-interactions）が守られている（SWC-107）
- [ ] 外部呼び出しの前にすべての状態変更が完了している
- [ ] 可能な限り`transfer()`関数を使用して外部コントラクトにイーサを送信している
- [ ] リエントランシーガードが適切に実装されている
- [ ] 外部コントラクトが現在の関数に再入した場合の影響が検討されている
- [ ] 外部コントラクトが別の関数に再入した場合の影響が検討されている

### 算術オーバーフロー/アンダーフロー

- [ ] SafeMathまたは0.8以降のチェック付き数学を使用している（SWC-101）
- [ ] `unchecked`ブロックの使用が文書化されている
- [ ] 各`unchecked`操作について、オーバーフロー/アンダーフローが発生しない理由が説明されている
- [ ] 乗算がオーバーフローする可能性がある場合を除き、常に除算の前に乗算している

### 外部呼び出しと依存関係

- [ ] 外部コントラクト呼び出しの結果がチェックされ、エラーが処理されている（SWC-104）
- [ ] 外部呼び出しが失敗した場合のDoSの可能性が検討されている（SWC-113）
- [ ] 低レベル呼び出しを行う場合、呼び出す前にコントラクトが存在することを確認している
- [ ] `address.transfer()`や`address.send()`の代わりに`.call.value(...)("")`を使用している（SWC-134）
- [ ] 外部コントラクトが何をするか、何を返すかについての前提がチェックされている

### アクセス制御

- [ ] `onlyOwner`/`requiresAuth`などの正しいモディファイアが適用されている
- [ ] 認証に`tx.origin`を使用していない（SWC-115）
- [ ] 関数が信頼されたユーザーによってのみ呼び出される場合でも、すべてのパラメータが安全な範囲内にあることを検証している
- [ ] `msg.sender`が常に関連するユーザーであると仮定していない

### その他の脆弱性

- [ ] `block.timestamp`は長い間隔にのみ使用している（SWC-116）
- [ ] 経過時間にblock.numberを使用していない（SWC-116）
- [ ] 特に外部コントラクトへのdelegatecallは可能な限り避けている（SWC-112）
- [ ] ランダム性に`blockhash()`などを使用していない（SWC-120）
- [ ] 署名はノンスと`block.chainid`でリプレイから保護されている（SWC-121）
- [ ] すべての署名がEIP-712を使用している（SWC-117 SWC-122）
- [ ] 2つ以上の動的型を使用する場合、`abi.encodePacked()`の出力をハッシュ化していない（SWC-133）
- [ ] 特定のETH残高を想定していない（SWC-132）
- [ ] 状態変数をシャドウイングしていない（SWC-119）
- [ ] DoSを引き起こす可能性のある無制限のループ/配列が使用されていない（SWC-128）
- [ ] 配列を反復処理中にその長さを更新していない

## コントラクト設計

### 設計原則

- [ ] コントラクトの継承が正しく、シンプルで線形に保たれている（SWC-125）
- [ ] 過度の継承を避け、複雑さを隠していない
- [ ] コントラクトが転送されたETHを受け入れるべき場合は、`receive() external payable`関数を使用している
- [ ] 保存された状態間の関係に関する不変条件が文書化されテストされている
- [ ] 可能な限り既知/確立されたライブラリを使用している（OpenZeppelinコントラクトなど）

### トークン関連

- [ ] ERC20標準に準拠している
- [ ] ERC-777トークンとの相互作用におけるリエントランシーの可能性が考慮されている
- [ ] 転送時手数料トークンのサポート状況が文書化されている
- [ ] リベーシングトークンのサポート状況が文書化されている
- [ ] 小数点が多すぎるまたは少なすぎるトークンのサポート範囲が文書化されている

### DeFi特有の考慮事項

- [ ] AMMからのスポット価格をオラクルとして使用していない
- [ ] オラクル/価格操作を防ぐために健全性チェックを使用している
- [ ] 内部会計と実際の残高を混同していない
- [ ] コントラクト内のトークンの生の残高に依存することの影響が検討されている

## ガス最適化

- [ ] 複数回読み取られるストレージスロットが最適化されている
- [ ] 値をその場で計算する方が保存するよりも安い場合、計算が優先されている
- [ ] オーバーフロー/アンダーフローが不可能な場所では、`unchecked`ブロックを使用している
- [ ] 最適化が行われる場所には、それらが節約するガスの見積もりとともに説明がコメントされている
- [ ] 可能な限り、分岐ロジックを簡素化するために三項式が使用されている

## テストとカバレッジ

- [ ] 「ハッピーパス」のユーザーストーリーのテストがある
- [ ] 失敗するはずのアクションに対してリバートを期待するテストがある
- [ ] すべてのテストが合格している
- [ ] ファズテストが組み込まれている（Foundry、Echidnaなど）
- [ ] 静的解析ツール（Slitherなど）がコードで実行され、その結果が検討されている
- [ ] 可能であれば形式検証ツールが使用されている（Certora、Runtime Verificationなど）
- [ ] テストによって提供される全体的なラインカバレッジの割合が高い

## ドキュメンテーション

- [ ] コントラクトの目的と他のコントラクトとどのように相互作用するかがnatspecを使用して文書化されている
- [ ] すべての関数が文書化されている（`public`/`external`関数にはNatSpecドキュメントを使用）
- [ ] 外部のセキュリティ前提条件が文書化されている
- [ ] 精度の損失をもたらす可能性のある算術演算が文書化されている
- [ ] リエントランシーロックが使用される場合、その必要性の理由が文書化されている

## デプロイメントとアップグレード

- [ ] デプロイスクリプトとモックアップグレードスクリプト（該当する場合）が準備されている
- [ ] デプロイメントテストが書かれている
- [ ] Etherscanでコントラクトを検証する計画がある
- [ ] GitHubリポジトリに、コントラクトがデプロイされるアドレスが記載される予定
- [ ] UIからGitHubリポジトリへのリンクが提供される予定

## インシデント対応

- [ ] セキュリティ連絡先メールアドレスがREADME.mdファイルに目立つように表示される予定
- [ ] バグ報奨金プログラムの設定計画がある
- [ ] モニタリングとアラートの設定計画がある
- [ ] エクスプロイトが発生した場合にコントラクトを一時停止したり、他の防御アクションを取るための緊急アクションスクリプトが準備される予定
- [ ] インシデント対応計画が作成される予定

## 監査プロセス

- [ ] 監査前に[監査準備チェックリスト](https://github.com/nascentxyz/simple-security-toolkit/blob/main/audit-readiness-checklist.md)が完了している
- [ ] 監査中に不明な点がある場合、または監査人により多くの時間を費やしてほしい領域がある場合、これらのリストが作成されている
- [ ] 監査人のためのスコーピング詳細が提供されている
- [ ] 監査が実施された後、監査で提案されたパッチがデプロイされたコードに含まれることを確認する計画がある
- [ ] 監査中にコードに多数の推奨変更を受け取った場合、変更を加えた後に2回目の監査を受けることを検討している
